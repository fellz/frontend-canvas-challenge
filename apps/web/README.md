# @canvas/web — канвас «текст → генератор → результат»

React 19 + TypeScript + Vite, канвас — `@xyflow/react` (React Flow 12), маршруты — react-router,
серверное состояние — TanStack Query. Типы — из `@canvas/contracts`; бэкенд не менялся.

## Запуск

Нужны Node.js 24 и npm 11 (`.nvmrc` в корне). Из корня репозитория:

```sh
npm ci
npm run dev        # API на http://localhost:4001 (терминал 1)
npm run dev:web    # фронтенд на http://localhost:5173 (терминал 2)
```

Сборка и просмотр собранного:

```sh
npm run build:web      # apps/web/dist
npm run preview:web    # http://localhost:4173
```

Адрес API — `VITE_API_URL` (см. `.env.example`), по умолчанию `http://localhost:4001`.
`VITE_API_DELAY_MS=1000` в `apps/web/.env.local` добавит паузу перед каждым запросом, чтобы
разглядеть состояния сохранения и ожидания. `npm run check` в корне проверяет и форматирование фронтенда.

## Как устроена работа с API

```text
src/api/http.ts            request(spec) — единственное место отправки: адрес, заголовки, JSON-тело,
                           статус, пустой ответ (204/304), разбор тела, ETag/Location из заголовков,
                           ошибки сети/HTTP/разбора → ApiError {kind, status, code, requestId}.
src/api/endpoints.ts       вызовы как данные: путь, метод, тело, If-Match, Idempotency-Key.
                           graph.get/put дополнительно требуют ETag в ответе (контракт).
src/api/queries.ts         ключи и queryOptions: список пространств, граф (читается один раз при
                           открытии), генерации (refetchInterval, пока есть processing).
src/api/queryClient.ts     повтор только сети/5xx для всех запросов.
src/features/graph/store.ts   локальное состояние канваса (nodes/edges/viewport + revision).
src/features/graph/saver.ts   очередь сохранений: debounce, последовательные PUT, flush, 412, потеря ответа.
src/features/graph/model.ts   FlowNode-типы, fromGraph/toGraph (постоянные поля ↔ поля React Flow),
                           лимиты из схемы контракта.
src/features/graph/rules.ts   правило связей: типы, один вход, один выход генератора.
src/features/generation/   индекс генераций (одна Map по генератору, одна по результату) и запуск:
                           flush → POST с graphETag и Idempotency-Key.
src/features/nodes/        три ноды + общая рамка NodeShell (заголовок, удаление со связями).
src/lib/                   storage (JSON + подписка), idempotency (ключ на операцию).
src/ui/                    Button (pending), Notice/ErrorNotice, Async (загрузка/ошибка/данные), Field.
```

**Разделение обязанностей.** Транспорт ничего не знает о графе; `endpoints` — о состоянии;
`store` — о сети. Ноды не получают функций через `data`: контекст канваса (`useCanvas`) даёт им
`saver` и индекс генераций, а правки уходят через API React Flow (`updateNodeData`,
`deleteElements`, `addNodes`), которые в controlled-режиме превращаются в `onNodesChange` —
поэтому решение «нужно ли сохранять» принимается в одном месте по типу изменения
(`position`/`add`/`remove`/`replace` — да, `select`/`dimensions` — нет).

**Постоянные и служебные поля.** Сервер отдаёт ноды в форме, совместимой с React Flow, поэтому
при загрузке они используются как есть. При сохранении `toGraph` оставляет только `id`, `type`,
`position`, `data` у нод и `id`, `source`, `target` у связей — `selected`, `dragging`, `measured`
на сервер не попадают.

## Debounce и очередь сохранений (`saver.ts`)

- Каждое сохраняемое изменение увеличивает `revision` в store. Saver помнит `savedRevision`
  и ETag; правка → таймер 500 мс, серия правок → один PUT после паузы.
- PUT идут строго по одному (`running`). Пока запрос в полёте, правки продолжаются локально;
  после ответа цикл видит `revision !== savedRevision` и отправляет следующий PUT уже с новым
  ETag. Ответ PUT никогда не пишется в локальное состояние — берётся только ETag, так что
  старый ответ не затирает новые правки.
- `flush()` — сбросить таймер, дождаться, пока сервер получит текущую ревизию, вернуть ETag.
  Генерация вызывает его первой: сбой сохранения — ошибка на ноде, POST не отправляется.
- `412` → состояние `conflict`: локальные правки остаются, таймер не взводится, пользователь
  выбирает «Взять версию сервера» (GET → store.replace) или «Сохранить мою поверх» (GET за
  ETag → PUT локального).
- Сетевая ошибка PUT → `recover`: GET графа. Если ETag не изменился — PUT не дошёл, кнопка
  «Повторить»; если серверный граф равен отправленному — PUT дошёл, берём ETag и продолжаем;
  иначе — конфликт.
- Уход со страницы: `flush()` без ожидания и снятие подписки; опрос генераций прекращается сам —
  у запроса нет наблюдателей.

## Генерация

`useStartGeneration`: `await saver.flush()` → `POST /generations` с `{nodeId, graphETag, scenario}`
и `Idempotency-Key`. Ключ привязан к идентичности `{nodeId, graphETag, scenario, after}`, где
`after` — id предыдущей попытки: повтор того же запуска (двойное нажатие, потеря ответа) шлёт тот
же ключ, новый запуск после отказа — новый. Статус читается опросом списка генераций раз в
секунду, пока есть `processing`; `failed` — состояние в ответе 200, не HTTP-ошибка.

Нода результата показывает картинку только если генерация адресована ей (`resultNodeId`) **и**
её генератор подключён к ней сейчас (`useNodeConnections`). Переподключили цепочку — чужая
или старая картинка не показывается; список идёт от новых к старым, так что более новая попытка
всегда побеждает.

## Разбор участка обработки данных

`indexGenerations(list)` в `features/generation/generations.ts`.

- **Частота.** Вызывается через `select` TanStack Query — только когда список генераций
  действительно изменился: при опросе структурное сравнение сохраняет прежнюю ссылку на данные,
  и `select` не пересчитывается; без активной генерации опроса нет вообще.
- **Проходы.** Один `for…of` по списку. Список отсортирован от новых к старым, поэтому первая
  встреченная запись для ключа — актуальная (`has` перед `set`), без сортировки и без
  `filter`/`find` на каждую ноду.
- **Память.** Две `Map` с ссылками на объекты из кэша, элементы не копируются. Дальше каждая нода
  делает `get(id)` — O(1); без индекса каждая из до 20 нод искала бы по списку при каждом тике опроса.

Рядом: `toGraph` — один `map` по нодам и один по связям, плотные массивы (не `new Array(n)`
с дырками), вызывается один раз на PUT, не на каждую правку; `canConnect` — один проход по
связям без промежуточных коллекций, вызывается при перетаскивании связи.

## Проверенные сценарии

Прогонялись Playwright-скриптом на dev-сервере при ширине 1280:

1. Создание пространства → три ноды кнопками → связи перетаскиванием → текст. Через 500 мс
   `PUT` с `If-Match`; в сохранённом графе только поля контракта. Серия из 8 нажатий клавиш →
   один PUT.
2. Правка и сразу «Сгенерировать»: сначала сохранение последнего текста, потом POST — генерация
   запомнила именно его. Перезагрузка во время обработки: «Ждём изображение…», затем картинка
   в ноде результата, `succeeded` на сервере.
3. Тестовый отказ → «Генерация не удалась (SIMULATED_FAILURE)» → «Повторить» → успех. Двойное
   нажатие даёт одну генерацию: в списке две попытки `succeeded, failed`.
4. Связь «текст → результат» не создаётся; второй текст к занятому входу генератора — нет;
   удаление генератора убирает обе его связи, сервер принимает оставшийся граф.
5. Конфликт: граф изменён «другой вкладкой» (PUT через API) → локальная правка → `412` →
   правка остаётся в поле, сообщение и два действия. «Взять версию сервера» показывает серверный
   текст, дальнейшие правки сохраняются с новым ETag. «Сохранить мою поверх» записывает локальную.
6. Медленный PUT (1,2 с через `page.route`): правки во время запроса уходят следующим PUT,
   всего два PUT, на сервере последний текст.
7. При конфликте «Сгенерировать» показывает ошибку сохранения на ноде, генерация не создана;
   после разрешения конфликта запуск проходит.
8. После ухода со страницы запросов к `/generations` нет; возврат через «Последнее
   пространство» показывает готовый результат. Панорамирование сохраняет viewport.

## Известные недоработки

- Соединение портов только мышью — React Flow не даёт связывать ноды с клавиатуры; кнопки,
  поля и удаление (Delete/Backspace, кнопка ×) с клавиатуры работают.
- Черновик графа при конфликте живёт только в памяти вкладки: перезагрузка страницы во время
  конфликта возьмёт версию сервера.
- Сценарий «тестовый отказ» — флажок в ноде генератора, он не сохраняется в графе (контракт не
  предусматривает такого поля).
- Список генераций перечитывается целиком при каждом тике опроса (у API нет фильтра по ноде);
  при 20 нодах и одной активной генерации это один запрос в секунду.
- Автотесты в репозиторий не добавлены — сценарии выше проверялись внешним Playwright-скриптом.
